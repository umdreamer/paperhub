# PaperHub 本地软件需求与设计方案（讨论稿）

日期：2026-10-31。状态：需求讨论稿，尚未开始软件实现。

## 1. 目标与现状

在同一台电脑上，让 PaperHub 与 Zotero 共用本地 PDF。新文件进入指定目录后，PaperHub 应及时发现、核验、命名、归类和更新索引；PaperHub 或 Zotero 任一侧新增论文条目后，另一侧应能识别并同步。用户已确认这里的“同步共享”指同机使用，不要求软件自行实现跨设备 PDF 同步。

指定上游仓库 `https://github.com/umdreamer/paperhub.git` 已于本地克隆；2026-10-31 所检出提交为 `2a9cb122990803301fda80db46ebd2a02865e050`，仓库只有 MIT `LICENSE`，没有现成的 PaperHub 程序。本机文献库位于本仓库的上一级目录，已有 `PaperHub/`、`NewPaper/`、`PaperHub.html`、`PaperHub_iPad_WPS.html`、`PaperHub.xlsx`、`paperhub.bib` 和 `codex/` 内的一次性维护脚本。因此本项目是基于现有数据与规则开发新软件，不能假定上游已有同步能力。现查得 `PaperHub/` 下有 3023 个 PDF 文件；此数只是本次文件系统快照。

## 2. 范围与术语

“文件同步”是同机同一份 PaperHub PDF 与 Zotero 链接附件的对应关系；PaperHub 不直接修改 Zotero 的数据库文件。Zotero 原有存储附件需要先复制并核验到 PaperHub，原件保留。链接附件的文件位置变化应由软件通过 Zotero 接口协调更新，不靠手工修改 Zotero 数据库。

“条目同步”包括题名、作者、年份、刊会、DOI、分类、PDF 路径和 Zotero 条目键的映射。PDF 内容不由软件向 zotero.org 上传；Zotero 账户同步和多设备文件同步属于 Zotero 或用户另行配置的服务。Zotero 官方文档说明链接附件只保存路径，本身不随 Zotero 文件同步。这里的“及时”定义为文件事件到来后开始处理，并由周期性全量核对补漏；具体秒数在性能基线测得后确定，不能承诺操作系统事件零遗漏。

## 3. 功能需求

R1. 软件提供本地界面，显示监控目录、待处理文件、匹配证据、冲突、同步状态和最近一次成功生成的索引。默认监控同级 `NewPaper/`，允许增设受控目录；`PaperHub/` 是归档目录。首次启动只盘点，不自动重排整个旧库。

R2. 监听新增、改名和修改事件；文件大小及修改时间稳定后再读取。启动时及定时进行全量核对，以发现离线期间的变化和漏掉的事件。相同 SHA-256 文件标记为重复候选，保留原文件，不自动删除。

R3. 验证 PDF 文件头、结构、可读取首页和文件完整性。根据 PDF 首页、现有元数据、DOI 或 Zotero 条目确定题名、年份和刊会；字段缺失或互相矛盾时进入人工复核，不编造字段。非单篇论文、损坏文件和无法确认的材料留在原处并说明原因。

R4. 沿用现有归档结构 `PaperHub/一级主题/二级主题/` 和文件名规则 `年份-刊会-题名.pdf`。仅替换文件系统不允许的字符，保留题名中的有意义标点；同名不同内容不得覆盖，使用确定性的版本后缀并进入冲突复核。移动前生成逐项预案；执行时保留旧版本、记录原路径和 SHA-256 ，移动后复核内容及索引链接。大规模历史重命名须作为独立批次审阅。

R5. PaperHub 新增论文时，先按 DOI、已有 Zotero 键、题名加作者及年份逐级匹配；匹配结果唯一且证据充分时补充链接附件和缺失字段，不能覆盖用户已确认的元数据。找不到条目时创建 Zotero 条目及链接附件；多候选时交人工复核。同步写入使用 Zotero 支持的本地 API，获取用户授权的本地写入密钥。

R6. Zotero 新增条目时，软件定时读取变更：已有 PaperHub 文件则建立映射；只有 Zotero 存储附件时，复制文件到待处理区、核验后归档，并保留 Zotero 原件；只有元数据而没有 PDF 时，建立“待获取 PDF”记录，不生成虚假文件。Zotero 中修改题名等字段时先比较来源与时间，冲突进入复核，不用“最后写入者获胜”静默覆盖。

R7. 单一规范化清单保存稳定 PaperHub ID、Zotero 键、来源路径、现路径、SHA-256、元数据来源、核验状态和版本。`PaperHub.html`、`PaperHub_iPad_WPS.html`、`PaperHub.xlsx`、`paperhub.bib` 及现有 JSON 索引均由清单生成。生成到临时文件，校验行数、链接和格式后再替换正式文件；替换前保存旧版。一次导入失败不应留下部分更新的公开索引。

R8. 每次批处理留下可读报告和机器可读日志，包括发现、匹配、复制或移动、Zotero 写入、索引生成、失败及重试。界面提供重新扫描、重试、手工确认、撤销本轮导入的入口；撤销以保留的原文件及版本为依据，不执行内容删除。

## 4. 方案比较与建议

方案 A：继续扩展一次性脚本和定时任务。改动较少，但缺少持续状态、冲突复核界面和可靠的双向映射。方案 B：开发本地桌面程序，后台文件监听加周期扫描，统一清单与同步队列，复用或逐步替换现有生成器。推荐 B，便于逐阶段接入现有文献库并让每次变更可审计。方案 C：先建立远程服务和云端数据库。增加部署和数据边界复杂度，当前同机需求不需要。

建议分三期：第一期完成只读盘点、规则配置、导入预览和索引重建；第二期完成文件监听、PaperHub → Zotero 写入与安全回滚；第三期完成 Zotero → PaperHub 反向导入、冲突处理和持续运行。各期独立验收，旧库迁移始终是单独审批的批次。

## 5. 验收与风险边界

用真实本地测试目录验证：新 PDF 进入 `NewPaper/` 后被发现，稳定后完成核验；合格文件按规则命名并归类，四种输出及 JSON 索引指向同一文件；Zotero 中能打开该链接附件。反向测试 Zotero 新增的链接附件、存储附件和无附件条目。再测试重启补扫、同名不同内容、元数据冲突、API 暂不可用、索引生成失败和手工撤销。每例检查原文件和旧版仍存在、SHA-256 一致、没有重复 Zotero 附件、索引无坏链。真实 Zotero API 的读写权限和当前可用性尚未验证：本机配置显示已启用本地 API，但本次受执行环境限制，未连通服务，不能把方案写成已实现或已实测。
